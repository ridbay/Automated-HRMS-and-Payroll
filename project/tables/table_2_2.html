Table 2.2: Multi-tenant data isolation models compared

Isolation model Data separation mechanism Isolation strength Operational complexity Per-tenant cost Principal risk
Silo: database per tenant A dedicated database instance for each tenant Strongest; physical separation High: every migration, backup, and monitoring task is repeated per tenant High; a fixed overhead for every tenant regardless of size Operational drift, as a migration that partially fails leaves tenants on different schema versions
Bridge: schema per tenant A shared database instance, with a separate schema for each tenant Intermediate; logical, schema-bounded Moderate to high: migrations are applied schema by schema, and per-tenant customisation multiplies the variants to maintain Moderate Schema divergence between tenants, complicating upgrades and cross-tenant reporting
Pool: shared schema with tenant discriminator column † Shared database and schema; every tenant-owned row carries a tenant identifier Weakest; logical, query-bounded Low: a single schema and a single migration path for all tenants Lowest; cost grows with data volume rather than tenant count An unfiltered query that omits the tenant condition returns other tenants' rows, producing cross-tenant data leakage

† Model adopted in this project. The compensating controls it requires are set out in Section 3.6.1 and their implementation and testing in Sections 4.3.1 and 4.4.3.
