# ZenHR — Automated HRMS & Payroll Platform

## Comprehensive Project Overview & Technical Report

_Prepared as source material for a project report / thesis. Generated by direct inspection of
the codebase (source files, database schema, migration history, and git log) on 2026-09-07._

---

## Abstract

ZenHR is a multi-tenant Human Resource Management System (HRMS) and Payroll platform built to
automate the employee lifecycle for organizations operating under Nigerian statutory and tax
requirements. The system is implemented as a modern, serverless, edge-deployed web application:
a React single-page frontend and a Cloudflare Workers backend sharing one Cloudflare D1 (SQLite)
database, with per-company (tenant) data isolation and role-based access control layered on top
of JSON Web Token authentication. Beyond conventional HRMS functionality — workforce records,
onboarding/offboarding, attendance, leave, recruitment, performance management, benefits, and
asset tracking — ZenHR implements a full statutory payroll engine (PAYE, Pension, NHF, NSITF,
ITF) and an AI-assisted virtual HR assistant built on Cloudflare Workers AI with role-scoped,
auditable tool access. This report documents the system's architecture, data model, functional
modules, security model, development history, and testing approach in sufficient depth to serve
as the technical basis for a project report or thesis write-up.

## Chapter 1: Introduction

### 1.1 Background of the Study

Human Resource Management and Payroll processing are traditionally manual, error-prone, and
fragmented across spreadsheets, paper records, and disconnected point solutions — particularly in
small and mid-sized organizations. In jurisdictions such as Nigeria, payroll additionally carries
a non-trivial statutory compliance burden: progressive Pay-As-You-Earn (PAYE) income tax bands,
mandatory pension contributions, National Housing Fund (NHF) deductions, and employer-side
levies (NSITF, ITF), each with its own remittance schedule and reporting format. Manually
reconciling these obligations against attendance, leave, loans, and bonuses every pay cycle is
both labor-intensive and a significant source of compliance risk.

ZenHR was conceived as an integrated, single-platform answer to this problem: one system of
record for the entire employee lifecycle, with payroll computed directly from live employee,
attendance, and loan data rather than re-keyed from other systems.

### 1.2 Statement of the Problem

Organizations that rely on disconnected tools for HR and payroll face several recurring problems
that this project addresses directly:

1. **Data fragmentation** — employee records, attendance, leave balances, and salary data live in
   different systems, requiring manual reconciliation before every payroll run.
2. **Statutory compliance risk** — Nigerian PAYE, pension, NHF, NSITF, and ITF calculations are
   easy to get wrong by hand, and remittance deadlines are easy to miss without a tracked
   compliance calendar.
3. **Lack of role-appropriate visibility** — administrators, managers, and individual employees
   need different, correctly-scoped views of the same underlying data (e.g., a manager should see
   their team's leave requests, not the whole company's).
4. **Weak auditability** — HR/payroll changes (salary edits, role changes, settings changes) are
   sensitive and need a tamper-evident trail, which ad-hoc spreadsheet workflows do not provide.
5. **Multi-tenancy** — a platform serving more than one company must guarantee that one company's
   data is never visible to another, at every single query, not just at the UI layer.

### 1.3 Aim and Objectives

**Aim:** To design and implement a multi-tenant HRMS and Payroll platform that automates the
employee lifecycle end-to-end, with a statutory-compliant payroll engine and role-based,
auditable access control.

**Objectives:**

1. Design a relational data model capable of representing the full employee lifecycle
   (onboarding → active employment → offboarding) across HR, payroll, performance, and
   recruitment domains.
2. Implement secure, JWT-based authentication with role-based and permission-based authorization
   that scopes every data access to the correct tenant (company) and the correct role (Super
   Admin, HR Admin, Manager, Employee, Payroll Officer, Recruiter).
3. Implement an automated payroll engine that computes gross-to-net pay per employee, including
   Nigerian PAYE (progressive tax bands with Consolidated Relief Allowance), pension, NHF, NSITF,
   ITF, salary proration for mid-month hires, bonuses, and loan deductions.
4. Implement self-service and administrative workflows for attendance, leave, performance
   reviews (including 360-degree/peer feedback), benefits enrollment, asset tracking, and
   recruitment (applicant tracking).
5. Provide administrative visibility through dashboards, exportable reports, and an immutable
   audit log of sensitive actions.
6. Explore applied AI by embedding a role-scoped conversational assistant capable of answering
   HR/payroll questions through tool-calling against the live database, without ever bypassing
   the platform's own authorization rules.
7. Deploy the system on a serverless, edge-native infrastructure (Cloudflare Workers, D1, Pages)
   to minimize operational overhead and infrastructure cost.

### 1.4 Scope of the System

The system covers: workforce/employee records and organizational structure (departments,
locations); onboarding and offboarding as tracked "transition" workflows; attendance and
overtime; leave application and approval; recruitment requisitions and a full applicant-tracking
pipeline (candidates, interviews, scorecards, offers) with a public careers page; payroll
configuration, computation, run approval, and statutory remittance exports; performance
management (review cycles, self-assessments, manager reviews, peer/360 and upward reviews,
goals/OKRs, recognition/shoutouts); benefits and wellness (plan catalog, enrollment, dependents,
wellness programs, claims); asset management; a lightweight Learning Management System (LMS);
employee pulse/eNPS surveys; an internal support/helpdesk ticketing system; company-wide settings
and a "Control Center" (roles & permissions, holidays, email templates, integrations,
automation workflows, data export, audit logs); and an AI assistant. Out of scope / not yet
implemented: real third-party OAuth integrations (only Slack has a functioning webhook
connection), a native mobile application, and payroll disbursement (bank file export is
generated, but the platform does not itself move money).

### 1.5 Significance of the Study

This project demonstrates that a small engineering team (or an individual) can deliver a
production-shaped, multi-tenant SaaS HRMS on a fully serverless stack without provisioning or
managing servers, using an edge database, edge compute, and an edge-hosted inference API for the
AI feature — all under one Cloudflare account. It also demonstrates a concrete, auditable pattern
for safely exposing an LLM to sensitive HR/payroll data: giving the model tools rather than raw
data access, and re-deriving authorization inside every tool implementation instead of trusting
the model's own arguments.

## Chapter 2: System Architecture and Technology Stack

### 2.1 Architectural Style

ZenHR is a **two-tier client–server application** split into two independently deployable
projects inside one repository:

- A **React single-page application (SPA)** at the repository root (`src/`), compiled by Vite and
  deployed as static assets to Cloudflare Pages.
- A **stateless HTTP API** at `api/`, implemented with the Hono web framework and deployed as a
  Cloudflare Worker (edge compute — the same code runs in Cloudflare's global points of presence
  rather than a single origin server).

The two communicate exclusively over HTTPS/JSON; there is no server-side rendering and no shared
runtime between them. The backend follows a **strict layered architecture**:

```
HTTP request
   │
   ▼
routes/            Hono route definitions — path → middleware chain → controller (thin, no logic)
   │
   ▼
middlewares/        authMiddleware (JWT) → requireRole / requirePermission (RBAC) → tenantMiddleware (where used)
   │
   ▼
controllers/        Parses request, calls one service method, shapes the HTTP response
   │
   ▼
services/           All business logic, calculations, and orchestration live here
   │
   ▼
models/ (Drizzle)    Typed table schemas — the only layer that knows SQL/table shape
   │
   ▼
Cloudflare D1 (SQLite)
```

This mirrors a classic MVC-style separation of concerns adapted for an API-only backend: routes
are analogous to a router, controllers to a thin presentation layer, services to the "model"
(business logic), and Drizzle models to the persistence layer. The one documented exception is
the Settings / Control Center feature, whose routes call service classes directly with no
controller in between — a deliberate, acknowledged deviation rather than an oversight.

write volume, tenant-scoped reads). This keeps operational cost and complexity low — an important
consideration for a project of this scope built and operated by a very small team.

### 2.4 Request Lifecycle

A typical authenticated request (e.g., an HR Admin viewing the employee directory) flows as
follows:

1. The SPA calls `GET /admin/employees` with an `Authorization: Bearer <jwt>` header (issued at
   login) via the fetch wrapper in `src/api/client.ts`.
2. `authMiddleware` verifies the JWT's signature (`hono/jwt`, HS256) and, on success, sets
   `employeeId`, `companyId`, and `role` on the Hono request context.
3. `requireRole("SUPER_ADMIN", "HR_ADMIN")` rejects the request with `403` if the role doesn't
   match.
4. `requirePermission("workforce", "view")` performs an additional, additive check only if the
   employee has been assigned a custom fine-grained role (most employees have not, in which case
   this check is a no-op).
5. The route hands off to `getEmployees` in `employee.controller.ts`, which reads `companyId`
   from context and calls `EmployeeService.getEmployees(companyId, ...)`.
6. The service issues a Drizzle query scoped by `companyId` and returns typed rows.
7. The controller serializes the result with `c.json(...)`.

Every step from (2) onward is unit- or integration-tested in isolation (see Chapter 7).

### 2.5 Multi-Tenancy Model

ZenHR is **single database, shared schema, tenant column** multi-tenancy: every tenant
("company") shares the same D1 database and the same set of tables, and every tenant-owned row
carries a `company_id` foreign key. There is no per-tenant database or schema. Tenant isolation is
therefore entirely a function of **discipline in the service layer** — every query touching
tenant-owned data must filter by `companyId`, and the project's engineering conventions (see
`agent.md`) treat an unscoped query as a security bug, not merely a logic bug. `companyId` is
established per-request in one of two ways:

- From the verified JWT payload (`payload.companyId`) once a user is authenticated — the
  production path.
- From an `x-company-id` request header, accepted as a fallback by `authMiddleware` when no JWT
  is present. This exists to support mock/local-dev flows predating full JWT rollout and is a
  documented, deliberate compromise rather than an oversight (see Chapter 5 and Chapter 8).

### 2.6 Authentication and Authorization

- **Authentication**: password-based login (bcrypt-style salted hash — `hashPassword`/
  `generateSalt` in `auth.service.ts`) issuing an HS256 JWT containing `sub` (employee ID),
  `companyId`, and `role`. Tokens are stored client-side in `localStorage` alongside the
  authenticated user object.
- **Authorization** is two-layered:
  1. **Fixed-role gating** (`requireRole(...allowedRoles)`) — coarse-grained, per-route allow-list
     against six roles: `SUPER_ADMIN`, `HR_ADMIN`, `MANAGER`, `EMPLOYEE`, `PAYROLL_OFFICER`,
     `RECRUITER`.
  2. **Custom permission narrowing** (`requirePermission(module, action)`) — an employee may
     optionally be assigned a custom role (`roles` table) carrying a JSON permission matrix over
     six modules (`workforce`, `payroll`, `performance`, `settings`, `leave`, `attendance`) and
     five actions (`view`, `create`, `edit`, `delete`, `approve`). This layer can only **remove**
     access that the fixed-role gate already grants — it cannot grant access beyond a route's
     fixed-role allow-list. Employees with no custom role assigned are unaffected (the check is a
     pass-through).
- **Manager-scoped data** (e.g., "my direct reports' pending leave") is *not* enforced by
  middleware at all — it is filtered inside the relevant service method by comparing each row's
  `managerId`/`employeeId` against the caller's own ID, following a consistent pattern across
  `leave.service.ts`, `attendance.service.ts`, `goal.service.ts`, and `peerReview.service.ts`.

## Chapter 3: System Design

### 3.1 User Roles and Responsibilities

| Role | Description | Representative capabilities |
|---|---|---|
| `SUPER_ADMIN` | Highest-privilege administrator | Everything `HR_ADMIN` can do, plus company-wide settings and API key management |
| `HR_ADMIN` | HR/Finance administrator | Workforce CRUD, payroll configuration & run approval, recruitment settings, performance cycles, benefits admin, reports, Control Center |
| `MANAGER` | Line manager | Team-scoped attendance/leave approvals, team goal assignment, team performance reviews, team reports |
| `EMPLOYEE` | Self-service user | Clock in/out, apply for leave, view payslips, update profile, enroll in benefits, take courses/surveys, submit self-assessments |
| `PAYROLL_OFFICER` | Payroll specialist | Payroll dashboard, run submission, payroll-specific reports |
| `RECRUITER` | Recruitment specialist | Requisitions, ATS pipeline (candidates, interviews, offers), recruitment analytics |

Role is a fixed attribute on the `employees` table; a `MANAGER` becomes "a manager" purely by
having other employees' `managerId` point at them — there is no separate team/hierarchy table.

### 3.3 API Design

The API is organized under three top-level route groups mounted on the Hono app
(`api/src/index.ts`): `/auth`, `/public`, `/employee`, `/admin`, `/ai`, `/support`. `/admin` is
itself a composition of sub-routers (`payroll`, `leaves`, `job-requisitions`, `ats`,
`attendance`, `benefits`) mounted under one Hono instance, giving a predictable, resource-oriented
URL scheme, e.g.:

- `GET /admin/employees`, `POST /admin/employees`, `PUT /admin/employees/:id`
- `GET /admin/payroll/runs`, `POST /admin/payroll/runs/:id/approve`
- `GET /employee/me`, `POST /employee/leave/apply`, `POST /employee/attendance/clock-in`
- `POST /ai/ask`
- `GET /careers/:companyIdentifier` (public, unauthenticated — the SPA's one hand-rolled
  client-side route, everything else is tab-state navigation, not URL-routed)

A full endpoint-by-module count is included in Appendix B.

## Chapter 4: Functional Modules

### 4.1 Dashboard & Analytics

Role-specific landing dashboards: `HRDashboard` (company-wide KPIs) for `HR_ADMIN`/`SUPER_ADMIN`,
`PayrollDashboard` for `PAYROLL_OFFICER`, a generic `Dashboard` for employees, and
`ManagerDashboard` for managers (team headcount, pending approvals, team goals). Backed by
`dashboard.service.ts`'s `getDashboardStats`, which aggregates headcount, pending leave, open
requisitions, and payroll status into a single response.

### 4.2 Workforce Management

The employee directory and 360° employee profile (`Workforce.tsx`, `EmployeeDetail.tsx`,
`Directory.tsx`). Supports full CRUD on employee records, emergency contacts, document vault
(uploaded documents linked to an employee, and optionally to a specific performance
self-assessment as evidence), department/location assignment, temporary password reset, and a
per-employee audit-log view. Organizational structure (departments, locations, and department
membership) is managed here as well, via `org.service.ts`.

### 4.3 Onboarding & Offboarding (Transitions)

A generic "Transition" model represents either an onboarding or offboarding journey for one
employee, made up of a checklist of tasks categorized `HR` / `IT` / `Finance` / `Admin`, each with
an assignee, due date, and completion state. A transition's overall `stage`/`status` is derived
from its tasks rather than freely editable, keeping the two from drifting apart. Offboarding
additionally captures a reason (`Resignation` / `Termination` / `Contract Ended` / `Retirement`),
handover recipient, and exit-interview scheduling flag. New employees created in `onboarding`
status land in a dedicated `EmployeeOnboarding` self-service flow on first login rather than the
normal portal.

### 4.4 Attendance & Time Tracking

Clock-in/clock-out with optional geolocation capture (`latitudeIn/Out`, `longitudeIn/Out`,
free-text location labels), multiple sessions per day, computed work hours and overtime per
record, and a separate overtime-request approval workflow (employee submits hours worked outside
a scheduled shift with a reason/deliverable; a manager approves or rejects). Attendance policy —
start/end time, grace period, working-day calendar — is configured company-wide in
`company_settings` and drives the on-time/late classification applied at clock-in.

### 4.5 Leave Management

Employees apply for leave against a typed leave balance (`leave_balances`, one row per leave
type with a total entitlement); `leave.service.ts` computes days taken from approved requests on
the fly rather than storing a running balance, avoiding drift. Requests carry a status
(`pending`/`approved`/`rejected`), an optional attachment, and a manager comment. Managers see
only their direct reports' requests (service-layer filtering, not middleware); HR Admin/Super
Admin see everyone via a dedicated admin approvals screen (`AdminLeaveRequests.tsx`).

### 4.6 Recruitment & Applicant Tracking (ATS)

Two connected layers:

1. **Requisitions** (`job_requisitions`) — an approval workflow (`Pending Approval` → `Open` →
   `On Hold`/`Filled`/`Cancelled`/`Rejected`) capturing who requested and who reviewed a role,
   budget range, and justification, plus optional public-facing copy (`description`,
   `requirements`, `isPubliclyListed`).
2. **ATS pipeline** (`candidates`, `interviews`, `interview_scorecards`, `offers`,
   `candidate_timeline_events`) — a candidate progresses through `applied` → `screening` →
   `interview` → `offer` → `hired`/`rejected`. Interviews record per-interviewer scorecards
   (technical/communication/cultural scores plus a hire/no-hire recommendation) rather than one
   shared verdict, supporting panel interviews. Every stage transition, interview, and offer event
   is appended to a per-candidate timeline for a complete audit trail of the hiring decision.

A public, unauthenticated **careers page** (`/careers/:companyIdentifier[/:requisitionId]`) lets
external candidates browse open, publicly-listed requisitions and submit an application
(`JobApplicationForm.tsx`) that creates a `candidates` row with `source: 'Career Page'`. This is
the one route in the SPA reachable by a real URL rather than internal tab-state navigation.
`RecruitmentAnalytics.tsx` / `RecruiterDashboard.tsx` surface pipeline-stage funnels and
time-to-hire metrics.

### 4.7 Payroll Processing & Statutory Compliance

The payroll engine (`payroll.service.ts`) is the most computationally significant module in the
system. It runs entirely from live data — no manually re-entered figures — computed per employee,
per pay period:

**Per-employee computation (`computePayslip`)**

1. **Proration** — if the employee's hire date falls inside the target month and proration is
   enabled, the days from hire date to month-end are counted and gross pay is scaled by
   `proratedDays / daysInMonth`.
2. **Gross pay** — `annualSalary / 12`, prorated, plus any manually entered bonus override for
   that run.
3. **Salary split** — Basic Salary = 40% of prorated gross; Allowances = the remaining 60%
   (matching the default `salary_components` catalog, which is itself editable per company).
4. **Pension (employee)** — 8% (configurable) of the pensionable base (basic + allowances),
   deducted from net pay. The employer's matching 10% is computed and reported for remittance but
   never subtracted from the employee.
5. **NHF** — 2.5% (configurable) of basic salary, deducted from net pay.
6. **NSITF / ITF** — 1% (configurable) each of gross pay; both are **employer-borne costs**,
   tracked for compliance reporting but explicitly excluded from the net-pay subtraction.
7. **PAYE (income tax)** — computed on an annualized basis:
   - Consolidated Relief Allowance (CRA) = `max(₦200,000, 1% of annual gross) + 20% of annual
     gross` (togglable per company).
   - Taxable annual income = annual gross − CRA − annual pension contribution.
   - Tax is run through the company's progressive tax brackets (seeded with Nigeria's statutory
     bands: 7% / 11% / 15% / 19% / 21% / 24%, each fully editable), consuming each band's width in
     order so brackets can be freely re-ranged without breaking the math.
   - The resulting annual tax is divided by 12 for the monthly deduction.
8. **Loan deduction** — the lesser of the employee's active loan's fixed monthly installment or
   its remaining balance, so a nearly-paid-off loan doesn't over-deduct.
9. **Net pay** = gross pay − PAYE − pension − NHF − loan deduction − other manual deductions.

**Run lifecycle**: `previewRun` (unsaved, recomputed live) → `submitRun` (persists a
`payroll_runs` row plus one `payslips` row per employee, status `pending_approval`) →
`approveRun`/`rejectRun` → `markRunPaid`. Marking a run paid triggers two side effects
atomically alongside the status change: (a) every employee's active loan balance is decremented
by that period's deduction, generating a `loan_repayments` record, and closing the loan once fully
repaid; and (b) five `compliance_tasks` are auto-generated with real due dates (PAYE filing by the
10th of the following month, pension by the 7th, NHF/NSITF/ITF by the 30th), giving HR/Finance a
tracked remittance calendar rather than a manual tickler file.

**Reporting/export**: a bank disbursement CSV (employee, account, net pay) and five
scheme-specific remittance CSVs shaped to resemble each agency's actual filing format (PAYE
per-state, pension per-PFA, NHF and NSITF per-employee, ITF as a single company-level levy line).

**Other payroll sub-features**: configurable pay cycle/cutoff/payment day, minimum-wage
compliance checking, editable salary component catalog (earnings/deductions,
fixed/percentage-of-basic/percentage-of-gross), pay grades, and an "exceptions" list surfaced on
the payroll dashboard flagging employees missing bank details, an unconfigured salary, or missing
statutory IDs (PFA/pension ID/TIN) before a run is submitted.

### 4.8 Performance Management

A full review-cycle system: `review_cycles` (one company-wide cycle "active" at a time, e.g. "H2
2025") with a granular, named `cycle_stages` timeline (kickoff, peer selection, self-review,
manager review, etc.), each with its own start/due window. Within an active cycle:

- **Self-assessments** (`assessments`) — achievements, challenges, goal progress, skill ratings,
  a self-rating, and development goals, submitted by the employee then rated and commented on by
  their manager.
- **360° / upward reviews** (`peer_reviews`) — peer reviews require nomination and manager
  approval before the reviewer can submit; upward reviews (a report reviewing their manager) skip
  the nomination gate entirely.
- **Goals/OKRs** (`goals`) — individual, team, department, or company-scoped objectives with
  progress tracking (0–100%) and optional parent-goal linkage for alignment roll-ups.
- **Recognition** (`feedbacks`) — lightweight peer-to-peer "shoutouts" (praise/bravo/gratitude).
- **Training** (`employee_trainings`) — assigned/in-progress/completed training records, separate
  from the newer LMS module below.

Admins get company-wide analytics and a cross-employee assessment/goal browser
(`PerformanceManagement.tsx`); managers review their direct reports' pending self-assessments and
peer-review nominations; employees interact through a guided `AssessmentWizard.tsx`.

### 4.9 Benefits & Wellness

A plan-catalog model: HR defines `benefit_plans` (health, life, retirement, equity, perk,
wellness, FSA) with employer/employee cost split and coverage limits; employees enroll
(`benefit_enrollments`) and register dependents for family coverage. A separate wellness track
(`wellness_programs`/`wellness_participants`) runs fitness/mental-health/financial/nutrition
challenges with per-participant progress. Health-insurance and wellness-budget reimbursements
share one claims workflow (`benefit_claims`: submit → pending → approved/rejected), and an
approved wellness claim posts its amount against the employee's wellness budget usage. A legacy,
simpler per-employee financial snapshot (`employee_benefits`) remains the source of truth for the
numbers shown on the compensation/payslip views.

### 4.10 Asset Management

Company-owned equipment (`employee_assets`) assigned to employees, tracked by category, serial
number, condition, purchase value, and assignment status — both a company-wide asset registry
(`AssetManagement.tsx`, admin) and a personal "my assets" view for employees.

### 4.11 Learning Management System (LMS)

A lightweight LMS: admins create `courses` (external video/SCORM link, duration) and assign them
to employees, creating a `course_enrollments` row tracked through `assigned` → `in_progress` →
`completed` with a 0–100% progress value. Employees track and update their own progress via
`TakeCourseModal.tsx`; admins see per-course enrollment/completion rosters via `LMSAdmin.tsx`.

### 4.12 Employee Surveys

Admin-authored `surveys` (eNPS, pulse, or custom type) targeted at all employees or a specific
department, made up of ordered `survey_questions` (rating, free text, or multiple choice).
Responses are optionally anonymous (`employeeId` nullable on `survey_responses`); each answer is
stored per-question in `survey_answers`. Admins view aggregate results per survey
(`SurveysAdmin.tsx`); employees complete active surveys via `TakeSurveyModal.tsx`.

### 4.13 Support / Helpdesk

An internal ticketing system (`support_tickets`, categorized IT/HR/Payroll/General, prioritized
Low–Urgent, `Open`/`In Progress`/`Resolved`) with a threaded message log per ticket
(`support_ticket_messages`) shared between the employee and HR/admin.

### 4.14 Settings & Control Center

Company profile (name, logo, industry, fiscal year), security settings (2FA requirement,
password policy, session timeout), the operational calendar (working days, public holidays),
custom role/permission management, API key issuance, transactional email template editing, a
third-party integration catalog (Slack has a real webhook-based connection flow — an admin pastes
an Incoming Webhook URL and can send a test message with delivery status tracked in
`integration_events`; every other cataloged integration is a seeded on/off toggle with no live
handshake behind it yet), an automation "workflows" catalog (named step checklists, enable/disable
only — no execution engine behind it), a full company data export (JSON dump of every table for
the tenant), and a searchable, filterable, exportable audit log of sensitive administrative
actions (`audit.service.ts`, invoked from nearly every mutating admin route).

### 4.15 AI Assistant

An embedded conversational assistant (`AIAssistant.tsx` on the frontend; `ai.service.ts` on the
backend) built on **Cloudflare Workers AI**, using `@cf/meta/llama-3.3-70b-instruct-fp8-fast` with
native function-calling. Architecturally, this module is the project's applied-AI contribution and
is designed around one governing principle: **the model is never trusted to enforce access
control — every tool re-derives its own authorization from the caller's verified identity.**

- Eight read-only tools are exposed: `getEmployee`, `searchEmployees`, `getLeaveBalance`,
  `getPendingLeaveRequests`, `getHeadcount`, `getPayrollSummary` (aggregate totals only, never
  individual salaries), `getOpenRequisitions`, `getComplianceTasksDue`.
- Each tool implementation independently checks the caller's role and, for manager-scoped tools,
  cross-references the caller's direct-report set before answering — even if the model requests
  data belonging to someone else. A tool that would expose out-of-scope data returns a structured
  `{ error }` object instead of the data, and the system prompt instructs the model to relay that
  refusal plainly rather than attempt another tool as a workaround.
- The agent loop caps at four tool-calling iterations before returning a "this needs to be
  broken down further" response, bounding cost and latency.
- Every question is appended to `ai_query_logs` (company, employee, role, question, tools used),
  giving Compliance/Settings a genuine usage and access trail — useful both operationally and as
  evidence of correct scoping behavior.
- The endpoint (`POST /ai/ask`) requires a real, verified JWT; the tenant-header-only auth
  fallback used elsewhere in the API is explicitly rejected here, because it carries no `role`
  claim for the tool-scoping logic to key off.

## Chapter 5: Security, Compliance, and Auditability

- **Transport & CORS**: all API traffic is HTTPS (Cloudflare-terminated); CORS is enabled
  globally on the Worker.
- **Password storage**: salted hashes (`generateSalt`/`hashPassword` in `auth.service.ts`), never
  plaintext; a "temporary password reset" flow forces `isPasswordChanged` back to `false`.
- **Token-based auth**: HS256 JWTs signed with a per-environment secret (`JWT_SECRET`, falling
  back to a hard-coded local-dev value only when unset — a gap flagged for production
  hardening in Chapter 8).
- **Tenant isolation**: enforced at the service layer via `companyId` filtering on every
  tenant-owned query; the project's engineering guidelines treat an unscoped query as a security
  bug on par with a cross-tenant data leak, not merely a correctness issue.
- **Role-based + permission-based authorization**: see §2.6 — two composable layers, with the
  fine-grained layer strictly additive/narrowing over the coarse-grained one.
- **Auditability**: `AuditService.log(...)` is invoked from settings, company profile,
  departments, locations, roles, holidays, email templates, integrations, workflows, and data
  export routes, recording actor, action, module, severity, free-text detail, and the requester's
  IP (`cf-connecting-ip`). Logs are queryable and CSV-exportable from Settings ▸ Audit Logs.
  Per-employee audit history is also exposed on the employee 360° profile.
- **AI-specific safeguards**: see §4.15 — capability-scoped tools, mandatory JWT, and a persistent
  query log.
- **Known, documented compromises** (see Chapter 8 for full detail): an `x-company-id`
  header-only authentication fallback still accepted on most `/admin` routes for legacy/mock
  flows, and a default JWT secret used only when the environment variable is absent.

## Chapter 7: Testing and Quality Assurance

The backend is tested with **Vitest**, organized as **57 test files (≈4,712 lines)** under
`api/tests/`, mirroring the structure of `api/src/` one-for-one. Three testing patterns are used
consistently:

1. **Service unit tests** — the Drizzle `db` object is mocked as a chainable stub
   (`vi.fn().mockReturnThis()` for query-builder methods, `vi.fn().mockResolvedValue(...)` for
   terminal calls) and injected directly into the service instance. Tests assert both the
   returned value and that the correct database calls were made — in particular, that
   authorization short-circuits happen *before* any write (e.g., a manager acting on someone
   outside their team must return an error without ever calling `update`).
2. **Controller unit tests** — the service module is mocked, and the controller function is
   invoked directly against a hand-built mock Hono `Context` (`req.query`/`req.param`/`req.json`,
   `env`, `get`, `json`), asserting the service was called with the right arguments and the
   response payload/status is correct.
3. **Integration tests** — `index.test.ts` exercises the real Hono app end-to-end via
   `app.request()` with `hono/jwt`'s `verify` mocked, validating routing and auth behavior through
   the full middleware chain rather than any single layer in isolation.

New Drizzle queries are expected to be tested against empty results, not-found cases, and
cross-tenant access attempts specifically, since a tenant-scoping bug is treated as a security
defect. **The frontend currently has no automated test harness** (no Vitest/RTL wiring in the
root `package.json`) — this is an acknowledged, explicitly flagged gap rather than an oversight,
and is listed again in Chapter 8.

At the time of writing, the test suite could not be executed in this environment (dependencies
were not installed, and the local Node.js version was below the project's supported range), so
current pass/fail status should be re-verified with `cd api && npm run test:run` before citing
specific pass counts in a final report.

## Chapter 8: Limitations and Known Gaps

1. **Authentication fallback** — `authMiddleware` still accepts an `x-company-id` header as a
   substitute for a verified JWT on most `/admin` routes, a deliberate but security-relevant
   compromise carried over from a pre-JWT mock-data phase of development.
2. **Default JWT secret** — falls back to a hard-coded string when `JWT_SECRET` is not set in the
   Worker environment; production deployments must set this explicitly.
3. **Incomplete third-party integrations** — the Control Center integrations and automation
   workflows catalogs are seeded on/off toggles with no real OAuth handshake or webhook execution
   engine behind them, with the single exception of Slack (a genuine, working webhook
   integration).
4. **Object storage not yet provisioned** — the R2 bucket referenced in `wrangler.toml`
   (`zenhr-storage`, for employee documents and candidate résumés) does not yet exist in the
   target Cloudflare account; company logos are currently stored as inline data URIs instead as a
   workaround.
5. **No automated frontend testing** — unit/integration coverage exists only for the backend.
6. **No CI/CD pipeline** — deployment is a manual, developer-run process (`wrangler deploy`,
   `wrangler pages deploy`), with no automated build/test gate before release.
7. **Single active review cycle assumption** — the performance module assumes one company-wide
   "active" review cycle at a time, which may not suit organizations needing overlapping or
   department-specific cycles.
8. **Statutory remittance cadence simplification** — NSITF/ITF compliance tasks are generated
   every payroll run even though these levies are typically remitted quarterly or annually in
   practice; the system currently favors uniform, guaranteed tracking over precisely modeling
   each scheme's real cadence.
9. **No payment execution** — the platform generates bank-transfer and remittance files but does
   not integrate with a payment rail to actually disburse funds.

## Chapter 9: Future Work and Recommendations

1. Remove the `x-company-id`-only authentication fallback from production once all client flows
   are confirmed to authenticate via JWT, closing the RBAC bypass it currently permits.
2. Provision the R2 bucket and wire real document/résumé upload through `storage.service.ts`.
3. Build a genuine OAuth-based integration framework (starting with the highest-value integration
   — e.g., a payroll disbursement API or an accounting system) to replace the seeded
   integrations catalog.
4. Add a frontend automated test suite (Vitest + React Testing Library is a natural fit given the
   existing Vite toolchain), prioritizing components with real branching logic (onboarding
   wizard, assessment wizard, payroll preview).
5. Introduce a CI pipeline (e.g., GitHub Actions) running `npm run test:run` and a production
   build on every push, gating deploys on green tests.
6. Extend the performance module to support multiple concurrent or department-scoped review
   cycles.
7. Integrate a real payment/disbursement API so payroll runs can move from "bank file generated"
   to "funds actually disbursed" within the platform.
8. Refine NSITF/ITF compliance-task generation to match each scheme's real statutory filing
   cadence instead of generating a task every payroll run.
9. Expand the AI assistant's tool set (e.g., write-capable tools behind explicit
   confirmation steps, or company-wide analytics summarization) once the read-only tool set has
   been operated safely in production.

## Chapter 10: Conclusion

ZenHR demonstrates that a comprehensive, statutory-compliant HRMS and payroll platform can be
built on a modern serverless/edge stack with disciplined layering (routes → controllers →
services → typed models), a consistent multi-tenancy and role-based access control model, and a
test-first backend culture. The payroll engine in particular shows that non-trivial domain logic
— progressive tax computation, statutory contribution handling, proration, and loan
amortization — can be implemented transparently and auditably in ordinary application code rather
than a black-box calculation service. The AI assistant module further demonstrates a defensible
pattern for integrating a large language model into a system handling sensitive HR and payroll
data: by treating the model purely as a natural-language front end over a fixed, pre-authorized
set of tools — and never as an authority on what it is allowed to see — the system keeps its
existing access-control guarantees intact even as an LLM is added to the request path. The
documented gaps (Chapter 8) are explicit engineering trade-offs made to prioritize breadth of
functionality within the project's timeframe, and the recommendations in Chapter 9 offer a
concrete roadmap for hardening the platform toward production readiness.
